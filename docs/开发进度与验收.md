### 批次 4 的核心设计判断

**样品不是「皮肤的描述」，而是「皮肤本身」。**

原先每套皮肤用「图标 + 4 格色卡」表示。规范 §12.1 要的是**琴键样品板**，
而 §46 说皮肤是「给真实乐器更换材质」——于是 `SkinSample` 直接渲染一段**真实琴键**：
4 个白键 + 2 个黑键，白键层流式、黑键层绝对定位（和真键盘同一套 §10.3 结构），
颜色来自同一套 `--skin-*` 变量。**孩子看到什么，弹到的就是什么。**

这也让「删除 `mark` 徽章字段」成为正确选择：既然样品就是那块材质，
再用一个 `leaf` / `flame` 符号去指代它，就是 §0.9 说的多余元素。
完成页的「新获得」也从图标换成了材质样品。

### 批次 3 的验证方式：把 §47 变成数学

`src/features/skins/skins.contrast.test.ts` —— **97 个用例，每套皮肤 12 项 WCAG 对比度断言**。

§47「无论任何皮肤：音名可读 / 黑白键关系可辨 / 高亮状态明确 / 按下状态可见」是少数
**能用数学验证**的设计规则，因此把它实现成了可执行约束：

| 断言 | 阈值 | 依据 |
| --- | --- | --- |
| 音名可读（白键 / 黑键标签） | ≥ 4.5:1 | WCAG AA 正文 |
| 黑白键关系可辨 | ≥ 3:1 | WCAG AA 非文本图形 |
| 高亮状态明确（引导色 vs 对应键面） | ≥ 3:1 | 同上 |
| 按下状态可见（静止 vs 按下） | ≥ 1.15:1 | 看得出来但克制 |
| 边界可辨 | ≥ 1.1:1 | §10.2 要求 1px 边界 |
| 键面渐变两端 | ≤ 1.12:1 | §10.2「极轻微纵向明暗」不是玻璃渐变 |
| 带渐变的字段数量 | ≤ 2 | §11.4 皮肤强度 70/20/10 |

**这套测试上线时立刻抓出了三个真实缺陷**（不是笔误，是会伤到孩子的可用性问题）：

1. **7 套皮肤的高亮色在黑键上对比度只有 1.9–2.9:1** —— 根因是我设计了一个耦合：
   用一个 `--skin-guide` 同时服务浅色键面和深色键面。数学上这两个要求把亮度夹进一个
   很窄的区间，深色皮肤甚至无解。改为 `--skin-guide` / `--skin-guide-on-black` 两个变量后解除耦合。
   规范要求的是「高亮明确」，不是「高亮同色」。
2. **夜空 / 太空的黑白键对比度只有 1.54:1** —— 深色皮肤把「白键」也做得很暗，
   孩子根本分不出键位。按 §47 的优先级（可弹 > 可辨 > 可学 > 好看），
   琴键回到中间调，把「夜色」交给舞台背景表达。
3. **一个测试自身的 bug**：`gradientStops()` 会匹配纯色 hex，导致「带渐变的字段数」恒为 7。
   改为判断是否含 `gradient(`。

## 录音回放

**Phase 2 的最后一块。** 完成页多了一个「听我弹的」按钮，回放刚刚这一遍演奏。

### 回放的是「我弹的」，不是「示范」

这条决定了整个实现方式。回放必须包含：

- **弹错的音** —— 那正是孩子刚才做的事，剔掉就成了假的
- **抢拍 / 拖拍** —— 用真实的时间间隔，不量化到拍子
- **每个音按了多久** —— 戳一下就走和按住不放，听起来必须不一样
- **力度** —— 触控笔/压感设备上的轻重会被还原

所以它听起来有孩子自己的节奏感。这与「听一遍」（`scheduler.ts`，按谱面播放）是**两件事**，
两者共用 `audioEngine.playScheduled` 与同一条 `AudioContext` 时间轴。

### 数据：为什么要开一条新时间轴

原计划是复用 `PerformanceEvent`（`scoring.ts` 的注释里写着「一份数据同时服务评分、复盘、回放」），
但实际做下来发现它**不够**：评分只需要「音高 + 时刻」，回放还需要**松开时刻**与**力度**。

于是新增 `PracticeStateShape.timeline`（`PerformanceStep`），与 `events` 分开：

| | 关心什么 | 谁在用 |
| --- | --- | --- |
| `events`（`PerformanceEvent`） | 音高对不对、早到晚到 | 评分 |
| `timeline`（`PerformanceStep`） | 何时按下、何时松开、多大力 | 录音回放 |

分开的收益很直接：**加回放没有改动 `scoring.ts` 一行**，也不需要往评分事件里塞回放字段。
有一条测试专门钉住这件事 —— 同一串按键，有没有记时间轴，`ScoreBreakdown` 完全一致。

### 实现要点

| 位置 | 做法 |
| --- | --- |
| `practiceReducer.ts` | `playing` 期间记录 `on` / `off`；`velocity` 从 `notePressed` 带进来；上限 `MAX_TIMELINE_STEPS = 1200`（孩子乱按也撑不大内存） |
| `recording.ts` | `buildRecording()` 纯函数：按音名配对 `on`/`off` 算出真实按住时长、时间归一化到 0、夹取（60ms ~ 4s）、留缝；`startRecordingPlayback()` 排程 |
| 排程 | 与听一遍同一个原则：**统一排程到 `AudioContext` 时间轴**，不用「每个音一个 setTimeout」。整段回放只有一个定时器负责收尾 |
| `ResultOverlay.tsx` | 「听我弹的」按钮；播放中变成「停止」。离开完成页时自动停掉，否则声音会跟着走 |

两个刻意的降级选择：

- **没有可回放的音就不显示按钮**（空录音不给一个点了没反应的按钮）
- **音频没就绪时静默降级**：按钮照样走完一轮，而不是死在那里。
  与「听一遍」同一个约定（`ensureReady()` 的返回值不检查）

### 验证方式

jsdom 里没有 `AudioContext`，所以分三层测：

1. **纯函数层**：`recording.test.ts` 覆盖配对、兜底时长、夹取、归一化、错音保留、纯函数性
2. **排程层**：`vi.mock` 假引擎，断言「每个音只排程一次」「时刻 = currentTime + 余量 + 相对时刻」
   「整段只有一个定时器」「`stop()` 立刻静音且不再回调」
3. **端到端**：`app.smoke.test.tsx` 弹完整首 → 完成页出现「听我弹的」→ 点下去变成「停止」→ 再点变回来

另外用 `npm run shot` 在真实布局引擎里跑了一遍完整流程（`scripts/flows/result-overlay.js`：
点开始 → 模拟 26 次真实 pointer 按键 → 等完成页），确认三个按钮在竖屏/横屏都**不重叠、
不溢出、内容完整可见**（探针输出 `buttonOverlaps: []`、内部滚动 0px）。

补曲方式：把旋律给我（简谱、音名+时值、或一个能看清谱面的链接）即可直接加进来，成本约 10 分钟/首。

### 加一首新曲的约定

1. 在 `songData.ts` 用 `seq([[音名, 时值(拍)], ...])` 写旋律，起始拍自动累加
2. 声明 `beatsPerBar`（3 或 4）
3. 跑 `npm run test` —— 数据完整性测试会自动检查：
   - 音名可解析、时长合法、音符不重叠
   - **总拍数是 `beatsPerBar` 的整数倍**（否则重拍力度会错位）
   - 音域跨度不超过一个八度 + 六度（否则会在键盘上被来回八度吸附）
   - 音域跨度、难度分布、分类筛选、`defaultKeyboard` 标注是否正确
   - 三档键盘下都能解析出可弹的音

### 表现力：重拍力度怎么来的

不在曲谱里手写每一个音的力度（400 多个音容易出错，而且改速度/换拍号就全废），而是由
`dynamics.ts` 按小节位置推导：

- 4/4 → 第 1 拍最强，第 3 拍次强，第 2、4 拍弱（倍率 `1.06 / 0.84 / 0.96 / 0.84`）
- 3/4 → 第 1 拍最强，第 3 拍次强，第 2 拍弱（倍率 `1.06 / 0.84 / 0.92`）
- 动态范围刻意压在 ±20% 以内：既能听出「有人在弹」，又不会让重拍显得做作；
  即使个别曲子小节对齐不完美，落错的「重拍」也只像人的自然起伏
- 曲谱里显式写的 `velocity` 优先于推导值（给个别需要特别强调/放轻的音用）

这条只影响**「听一遍」的播放**。孩子自己弹时的力度来自触控，而且绝不参与评分。

## 琴键物理尺寸（真实钢琴尺寸映射）

### 需求

让孩子在 iPad 上练琴时形成**能迁移到真实钢琴的手部姿势** ——
这要求屏幕上的琴键在**物理尺寸**上接近真实钢琴，而不是「按屏幕比例铺满」。

现代钢琴（DIN 8993 等标准）：**白键前缘 23.5 mm，一个八度跨度 164.5 mm**。

### 难点一：浏览器不告诉你物理尺寸

CSS 的 `mm` / `in` 在规范里被固定为 **1in = 96px**，与真实物理尺寸无关
（iOS Safari 与 Chrome 都遵守）。所以 `23.5mm` 写进 CSS 在任何设备上都是 88.8px，
在 iPad 上实际只有约 **17 mm** —— 而不是 23.5 mm。浏览器也没有 PPI 接口。

**解法**：用「已知机型表 + devicePixelRatio」反推。

```text
1 device px = 1 / ppi 英寸
1 CSS px    = dpr 个 device px
⇒ 1 mm      = ppi / (25.4 × dpr) 个 CSS px
```

验证：iPad（264 ppi / dpr 2）→ 1mm = 5.197 CSS px → **23.5mm = 122.1 CSS px**，八度跨度 854.9 CSS px。

命中不了机型表时退回兜底值并**标记为「估算」**，界面会带上「约」字 ——
宁可说「估算」，也不假装精确。

### 难点二：物理上装不下（这条无法用工程解决）

| 机型 | 横屏可用 | 屏幕物理宽 | 8 键 | 15 键 | 25 键 |
| --- | --- | --- | --- | --- | --- |
| iPad Pro 12.9 / 13 | 1334px | 263mm | **23.5mm ✓** | 17.1mm | 10.3mm |
| iPad Pro 11 | 1162px | 230mm | **23.5mm ✓** | 14.9mm | 8.9mm |
| iPad Air 10.9 | 1148px | 227mm | **23.5mm ✓** | 14.7mm | 8.8mm |
| **iPad 7 / 8 / 9（10.2"）** | **1048px** | **208mm** | **23.5mm ✓** | **13.4mm** | **8.1mm** |
| iPad mini 8.3 | 1101px | 177mm | 21.4mm | 11.4mm | 6.9mm |

**当前主力验证机型：iPad 第 7 代（10.2 英寸，2019）**
- 2160×1620 @ 264 ppi / dpr 2 → CSS 视口 810×1080
- 设备表命中 `'810x1080' → 264 ppi` ✓
- 屏幕物理宽度 207.8mm，横屏键盘可用 1048px = 201.7mm
- **8 键 = 23.5mm，八度跨度 164.5mm，与真实钢琴完全一致**；键盘总宽 977px，两侧各留白 35px
- 25 键只剩 42 CSS px 宽，**已接近 §25 的「核心操作 ≥44px」下限** —— 记录在此供产品决策，
  不是实现缺陷，是屏幕物理宽度决定的

**结论**：
- **产品只提供 8 键**，它也是唯一能在 iPad 上达到真实钢琴尺寸的档位（10.2" 及以上；
  iPad mini 屏幕只有 177mm 宽，差一点，约 21.4mm）
- 更宽的键盘必然更窄：15 个真实尺寸白键需要 352.5mm，而最大的 iPad 屏幕物理宽度只有 263mm。
  **这正是「只保留 8 键」的依据之一**（15 / 25 键的布局代码仍保留备查）。
  这是物理约束，不是实现取舍。
- 真实钢琴有 52 个白键、跨度约 1220mm —— 任何平板都只能显示其中一段。

### 实现

`src/features/piano/keySize.ts`：

- `REAL_WHITE_KEY_MM = 23.5`、`REAL_OCTAVE_SPAN_MM = 164.5`、`REAL_BLACK_KEY_RATIO = 0.58`
- `estimateDeviceMetrics()` —— 已知机型表 + dpr 反推 PPI（**纯函数，23 个单测覆盖各种机型**）
- `resolveWhiteKeyWidth()` —— 规则：**以真实尺寸为目标，放得下就用真实尺寸并居中留白，放不下才压缩；绝不放得比真实尺寸更大**
  （放大会让手指跨度超出真琴，反而破坏可迁移性）
- `describeKeyWidth()` —— 生成如实的一句话说明

`PianoKeyboard` 用 `ResizeObserver` 观察外层 `.pk-frame`（不是键盘自身，否则会
「测量 → 设定 → 再测量」形成循环），算出整块键盘的自然宽度写进 `--pk-natural-width`。
**内部的白键/黑键仍用百分比定位，所以放得下与放不下两种情况下布局都正确**——
这也正是当初选择「百分比 + 双层」结构（§10.3）的回报。

没有 `ResizeObserver` 的环境（老浏览器 / jsdom）退化为「量一次 + 跟随窗口变化」，
量不到就回到原有的铺满容器行为，功能降级但不会坏。

### 界面如何如实告知

- **练习页 / 自由弹**底部：显示 `白键 23.5 mm（真实钢琴尺寸）`，达到真实尺寸时标绿
- **`#/tuning` 自检页**：新增「琴键物理尺寸」面板 —— 设备 PPI（含估算来源）、设备像素比、
  白键实际宽度、真实钢琴白键宽度、实际八度跨度 vs 真实八度跨度

### ⚠️ 需要产品决策的一点（尚未实现）

**真实钢琴尺寸对幼儿的手可能偏大。** 成人手跨约 180–220mm，而 5–6 岁儿童约 100–120mm；
真实八度跨度 164.5mm 对幼儿是很大的伸展，强行去够反而会形成**错误姿势** ——
这与「培养手部姿势」的目标相反。

钢琴教育界对此有专门的解法：**窄键钢琴**（DS5.5 规格八度 139.7mm → 白键约 20.0mm；
DS6.0 规格八度 152.4mm → 白键约 21.8mm）。

因此建议后续增加一个设置项：**「真实尺寸 23.5mm / 适合小手 20–22mm」**，默认值需要你决定。
目前只实现了真实尺寸（按需求原文），没有自行增加这个设置（§29 不得自行增加 UI）。

### 现状：音频侧已经是零工作量

`velocity` 已经全链路打通：

```
useKeyboardInput → PianoKeyboard → usePianoAudio → AudioEngine.noteOn(note, velocity) → PianoVoice
```

`PianoSynth` 已经在用 velocity 驱动 4 个参数：

| 参数 | 作用 |
| --- | --- |
| `velocityToPeak` | 响度 |
| `brightnessScale(k, velocity)` | k ≥ 3 的高次谐波强度（敲得越重起音越亮） |
| `attackSec` | 越重起音越快 |
| 击弦噪声电平 | 两段噪声都按 `peak` 缩放 |

唯一的死点在 `src/features/piano/useKeyboardInput.ts` 的 `velocityFromPointer()`：触屏固定返回 `0.9`。

### 卡点：iPad 上拿不到可信的力度信号

| 信号源 | iPad 可用性 | 评价 |
| --- | --- | --- |
| `PointerEvent.pressure` | ❌ | 无压感硬件时规范要求恒为 0.5（实践中常为 0）。**iPad 全系没有力度感应屏**；3D Touch 是 iPhone 6s–XS 的，已停产 |
| `Touch.force` / `webkitForce` | ❌ | 同上，iPad 恒为 0 |
| Apple Pencil | ✅ | `pointerType === 'pen'` 的 `pressure` 是真实值，**今天就能出声**；但曲线是拍脑袋写的、没有测试覆盖 |
| `PointerEvent.width/height`（接触面积） | ⚠️ | 按重了指尖压平、面积确实变大，有真实信号但很脏：与「手指多大 / 按得多平」的相关性更强；滑奏时手指滚动会让面积剧烈抖动。需要按人校准 + 强平滑，**必须先真机实测**才知道能不能用 |
| 击键位置（落在琴键靠前还是靠后） | ✅ | **最有价值**。所有平台一致、确定性强、无需校准，物理上就是真实钢琴的杠杆原理。Y 坐标免费 |

### 推荐方案（真要做的时候）

主信号用**击键位置**，Apple Pencil 的 `pressure` 优先，接触面积只作为可选微调：

1. 命中测试从 `elementFromPoint` 改为「缓存一次容器 rect + 复用 `pianoLayout` 的 `leftPercent/widthPercent` 做纯几何计算」。
   顺带解决现有性能问题（每个 `pointermove` 强制重排），**并同时免费拿到 Y 位置**。这两件事是同一个改动。
2. 击键位置 → 力度：纯函数 + 单测。
3. 多信号融合 + 设置项「手感轻重」+ 曲线持久化。
4. 视觉反馈：让按下的力度看得见。

### 工作量

| 工作项 | 难度 | 工时 |
| --- | --- | --- |
| 击键位置 → 力度映射（纯函数 + 单测） | 低 | 0.5 天 |
| 命中测试改纯几何计算（缓存 rect + 拿到 Y） | 低 | 0.5 天 |
| 多信号融合（Pencil > 接触面积 > 击键位置） | 中 | 0.5 天 |
| 设置项「手感轻重」+ 曲线持久化 | 低 | 0.25 天 |
| 视觉反馈（力度可见） | 低 | 0.5 天 |
| **让孩子能发现这件事** | **高（设计风险）** | 1–2 天 + 真机迭代 |
| 真机调参（接触面积是否可用） | 中（不确定性高） | 0.5–1 天 |
| 测试回归 | 低 | 0.5 天 |

核心机制 1.5 天；要做到「孩子真的在用」是 **4–6 天**，其中一半花在可发现性与真机调参上。

### 决策时必须守住的三条

1. **绝不能进评分**。跟弹模式若按力度扣分，对孩子是灾难 —— 他们控制不了。力度只能是表现力，不是考核项。
2. **可发现性是最大风险**，不是代码。5 岁孩子不会知道「按琴键前缘更响」。需要琴键前缘渐变 / 自由弹一次性演示 / 力度可见化。**这决定功能是「能用」还是「看不见」。**
3. **与文档 §1.3 的产品排序的关系**：力度算「手感」的边缘，但它不回答「是否让孩子更容易开始弹、继续弹或学会一个音乐概念」。按 Phase 划分属于 Phase 2/3；真正准确的力度场景是文档 Phase 4 的 MIDI 外接。

### 更便宜的替代方案（建议优先）

`SongNote.velocity` 字段与 `playScheduled` 的 velocity 参数**都已经接好**，只是曲谱里没写。
给曲谱加力度标记（重拍强、弱拍弱、乐句收尾渐弱）只需改数据，**约几小时**，
而「音乐性」的提升立竿见影 —— 比触控力度更容易被孩子听出来。

## 按住提示（时值判定的第一步：先让它看得见）

### 先说清楚现状：现在**算不出**「长按 / 短按」的正确度

这是被明确问过的问题，结论是：**不能**。三处证据：

| 位置 | 实际情况 |
| --- | --- |
| `practiceReducer.ts` 的 action 列表 | 只有 `notePressed`，从来没有 `noteReleased` —— 按住时长从未进入状态机 |
| `PracticePage.tsx` 的 `handleNoteOff` | 拿到松开事件后**只调 `audioEngine.noteOff()`**，连 `dispatch` 都没调 |
| `scoring.ts` | `accuracy = pitchScore × 0.7 + timingScore × 0.3`；`timingScore` 衡量的是**按下时刻**与「上一个音按下时刻 + 期望间隔」的偏差，不是单音长度 |

后果：整首全是四分音符和全是全音符，只要按键时刻对，得分完全一样；
一个 4 拍的全音符，10 毫秒点一下就松手，照样满分。

> 注意 `timingScore` **间接**包含时值：`expectedGapMs` 用的是相邻两音的拍差，
> 而连续音之间拍差恰好等于前一个音的时长。所以长音按太快确实会掉分 ——
> 但窗口很宽（难度 1 是 750ms），而且屏幕上看不出「该等多久」。缺的是**引导**，不是判分。

### 第一步（本次已做）：只让时长看得见，不参与任何评分

按对一个音之后：

1. **下一个键从强引导降级为弱提示**，直到按住的时间够了。
   这正是 §10.5 的引导层级（等的时候是弱外轮廓，可以弹的时候才给强高亮）。
   要解决的是「孩子还按着这个键，眼睛已经在找下一个键」。
2. **出现一道会走完的填充条**（`.pp__hold`），时长 = 音符自己的 `duration` × 拍速。

设计约束（都写进了代码注释，改这一段之前请先读）：

| 约束 | 理由 |
| --- | --- |
| **绝不参与评分** | `noteReleased` 不写 `PerformanceEvent`；`scoring.ts` 一行未改。有测试证明「弹了又弹 + 按了又按」与「完全没有松手这回事」得到**完全相同**的 `ScoreBreakdown` |
| **琴键始终可弹，早弹不额外扣分** | 按住提示是等待的视觉，不是闸门（§44 无羞耻错误机制）。键永远不会被禁用 |
| 时长用 `SongNote.duration`，**不是**相邻音拍差 | 有休止符时两者不同：休止符是**松开**，不是按住 |
| 松手就用 `holdReady()` 结束提示 | 不强迫孩子一直按住；iPad 上松手时机本来就不可靠（见《触控力度评估》的同类问题） |
| 减少动效时**不做连续填充** | 连续填充承载「还剩多久」的信息，压成 1ms 会变成一根永远满的条，反而说错话。改成只靠 §10.5 的两级引导表达 |
| 填充条沿用 `.pp__progress` 的语言 | §51 动效预算：本页已经有琴键动画与进度动画，不新增第三套 |

实现位置：`practiceReducer.ts` 的 `HoldGuide` / `holdReady()`，
`PracticePage.tsx` 的「按住提示」段，`practice.css` 的 `.pp__hold*`。

### 第二步（已完成）：先拿真机数据

判定要用的宽容系数不能凭猜，所以先把「孩子实际按住多久」量出来。

- `src/features/practice/holdStats.ts` —— **只写不判**的采样器：
  练习页每次确认松手就投一条 `{ note, targetMs, heldMs }`；
  没等到松手就被下一个音顶掉的，只计一个数（不投样本，因为它的 `heldMs` 无法确知）
- `#/tuning` 的「按住时长采样」面板把它读出来：样本数、没等到松手的次数、
  中位比值、短于一半的占比、按够了的占比，加一张分布条 + 最近 8 条明细

两个刻意的取舍：

| 取舍 | 理由 |
| --- | --- |
| **不落 localStorage** | 它不是成长数据，没有跨会话价值，也就不该去碰 `core/progress/storage.ts` 那条唯一的持久化通路。代价是刷新即清空，面板标题上写明了 |
| **有上限（最近 120 条）** | 统计看的是分布，样本够多之后再多的意义不大，避免长时间练习把内存撑大 |

**「没等到松手」的占比是这一步最关键的数字。** 它和样本数是成对的诊断指标：
如果它很大，说明松手信号在真机上不可靠，那就**不该**往下做判分 ——
这正是要在写判定之前先看清楚的事。采集清单见下方《真机验收清单 · 按住时长》。

### 第三步（尚未做，依赖第二步的数据）

1. **判定必须做成单边窗口**：按够了就满分，只在太短时衰减，
   和 `timingScoreForDelta` 同一个哲学 —— 松手晚绝不能扣分，
   真实钢琴上 legato（下一个音按下时上一个还没松）是正确的弹法。
2. **宽容系数由第二步的真实分布决定**，不能低于观测到的中位数。
3. **根本前提**：现在的跟弹是**步进式**的（弹对就立刻前进，孩子自己控制速度），
   上一个音按多久和下一个音什么时候弹没有耦合。严肃评时值需要「跟着节拍走」的模式，
   也就是 `Phase 3` 里还空着的**节拍挑战**。
   换句话说：即使第二步数据好看，正式评时值更可能属于节拍挑战，而不是跟弹模式。

## 外挂曲目与 PDF 导入评估（2026-05 结论：暂缓，方案已定）

需求原文：把《中国风钢琴入门教程》（王磊主编）的曲目以**外挂**形式置入程序，并提供**导入选项**，
让用户通过 PDF 曲目生成引导式教学练习。

### 必须拆成两件完全不同的事

| | 难度 | 结论 |
| --- | --- | --- |
| **外挂机制**（内容包 + 导入器） | ★☆☆☆☆ 低 | 架构天然支持，1 天可跑通 |
| **PDF 曲谱识别** | ★★★★★ 极高 | Web 端无可行方案，**不做** |

### 版权约束（决定了架构）

教材是已出版作品。民歌*旋律*多为传统/公有领域，但**编配（和声、伴奏型、指法、乐句处理）独立受保护**。

- ❌ **不能把教材曲目打包进仓库 / 构建产物**。应用要部署到 Cloudflare Pages 公开访问，
  那是公开传播他人享有著作权的编配作品。
- ✅ **"导入工具"本身中立**，App 不含任何教材内容，只提供导入能力。
- ✅ 用户**为自己家庭使用**、导入自己购买的教材、数据只存在自己设备上，接近个人使用 / 格式转换。

关键：这个法律约束与「让用户自己导入」的需求**指向同一个架构**。所以做导入能力既能满足外挂诉求，
又不需要承担分发风险。

### 技术真相：PDF 里没有「音乐」这层信息

这是整件事最重要的认知。PDF 里一个四分音符 C4 就是若干条贝塞尔曲线 + 线段的**绘制指令，
没有任何语义**。所以：

- 无论扫描件还是矢量排版 PDF，**都必须做 OMR（光学乐谱识别）**，是同一条技术路线，只是输入质量不同。
- **Web 端没有任何可用的开源 OMR**。Audiveris（唯一开源方案）是 Java 桌面/服务端程序，纯前端跑不了。

**已确认输入形态为「扫描件 / 拍照（图片型 PDF）」** —— 这是准确率最差的一档，
OMR 在拍照、页面弯曲、光照不均、可能有手写标注的真实场景下准确率约 40–70%。
**这条路线对本项目彻底关闭。**

准确率对孩子场景是致命的：30 个音的曲子错 3 个，就是在教错音，而且家长不会知道错在哪 3 个音。

### 各输入格式对比

| 输入 | 音乐语义 | 实现难度 | 准确率 | 结论 |
| --- | --- | --- | --- | --- |
| MusicXML | 完整（音高/时值/调号/连线/声部） | 中低 | ~100% | ✅ 首选 |
| MIDI | 有音高时值，缺记谱语义 | 中低 | ~95% | ✅ 次选 |
| 我们的 JSON 包 | 完整 | 低 | 100% | ✅ 兜底 |
| 矢量排版 PDF | 无 | 必须 OMR | 90–95% | ⚠️ 仍要 OMR |
| **扫描 / 拍照 PDF（本项目实际情况）** | 无 | 必须 OMR | **40–70%** | ❌ 不可用于教学 |
| **人工录入（PDF 当参考图）** | 完整 | 中 | **100%** | ✅ **本项目唯一可行路径** |

**服务端 OMR 也不走**：意味着用户教材要上传到服务器 —— 既违反「不依赖后端」的文档原则，
又把风险从「用户个人使用」升级为「你在服务器上存储处理他人版权内容」。

### 方案：PDF 降级为参考图 + 键盘录入

把 PDF 当作**参考图**，用人工点键生成曲谱：

- 准确率 100%；不需要 OMR、不需要后端、不需要上传
- **核心编辑器已全部现成**：三层键盘、pointer 输入、`AudioEngine`、`resolveSong`、`seq()` 记谱格式
- 家长做一首 30 音的小曲约 2–3 分钟，做完可试听、可反复使用
- 形态：左侧 PDF 页面（PDF.js 按需 `import()`，不阻塞首屏；或直接收 JPG/PNG 更轻），
  右侧键盘逐音点入，按小节自动分拍，实时试听，最后保存为内容包

### 工作量拆解

| 阶段 | 内容 | 难度 | 工时 |
| --- | --- | --- | --- |
| A. 内容包机制 | JSON schema、手写防御式校验（沿用 `migrations.ts` 风格）、ID 命名空间、独立存储、与内置曲库合并 | ★☆☆☆☆ | 1 天 |

### 架构建议

```text
src/core/content/            ← 与 core/progress 平行
├── packTypes.ts             ContentPack 类型
├── packSchema.ts            手写防御式校验
├── packStorage.ts           唯一允许碰内容存储的地方
├── ContentStore.tsx         第二个数据源
└── importers/{musicxml,midi,json}.ts

src/features/import/
├── ImportWizard.tsx
├── PackManager.tsx
└── NoteEntryTool.tsx        ← 核心
```

四条关键设计决策：

1. **ContentStore 与 ProgressStore 分开**。内容不是成长数据 —— 文档规则 5 说的是「成长数据走 ProgressStore」。
   内容包有自己的版本号与迁移层。
2. **导入曲目 ID 加前缀** `packId:songId`。保证 `bestAccuracyBySong` 的历史成绩不会串到别的曲子，
   也避免与内置曲目冲突。
3. **内容包是只读快照**，导入后不可变（要改就重新导入）。否则用户改包会让 ID 漂移，已有成绩对不上。
4. **参考图不持久化**。localStorage 只有 5MB，教材扫描件可能几十 MB。参考图只在录入时临时读取、
   不入库 —— 否则必须上 IndexedDB，复杂度翻倍。

### 副作用

导入曲目会让 `stats.songsCompleted` 增长更快，皮肤解锁节奏变松。不影响正确性
（`forest` 皮肤绑定的是具体 `twinkle-star` 这个 id），但需要知晓。

### 顺带可解决的既有问题

内容包机制做好后，可以顺手补上《曲目收录说明》里记录的**中文曲目缺口**：
用**公有领域的传统民歌旋律**（《茉莉花》《小放牛》《康定情歌》《沂蒙山小调》《凤阳花鼓》等）
配**我们自己的编配** —— 这是我们自己的作品，可合法发布，不需要抄教材。
「中国风」这个定位通过合法路径同样成立。

### 重新评估的时机

- 用户愿意提供 MusicXML / MIDI（则 D+E 变成首选路径，整体降到 3–4 天）
- 或者需要批量录入（超过 ~20 首）时，录入器的效率收益才明显
- 单独为了「一首教材曲子」而建整套导入体系不划算，届时直接用 `songData.ts` 加数据更快

## 五线谱与乐理（小挑战 · 看谱找键）

### 字形来源：Bravura，而不是手绘近似

谱号、音符头、临时记号全部是 **Bravura**（SMuFL 参考字体）的**真实雕刻字形轮廓**，
不是 SVG 手绘近似。

- 授权：SIL OFL 1.1，可自由嵌入与再分发（`LICENSES/Bravura-OFL.txt`）
- 做法：`scripts/extract-bravura-glyphs.mjs` 用 opentype.js 把 9 个字形转成 SVG 路径，
  产出 `src/features/notation/bravuraGlyphs.ts`（**自动生成，8.3 KB**）
- 为什么不用字体文件：完整 Bravura 是 868 KB，只为了 9 个字形加载整个字体不划算；
  抽成路径后既保持专业字形，又只增几 KB
- 重新生成：`npm run glyphs`（`.fontsrc/` 已 gitignore）
- 坐标方向已被抽取脚本自检钉住（Y 向下），`staffLayout.test.ts` 再验一次

### 音符形态：前两档全音符，第 3 档二分音符（这条踩过一次）

**第 1–2 档的音符一律是全音符：没有符干，也没有符尾。**

教材的识字顺序是「先认位置，再认时值」。全音符只有一个椭圆，
孩子的注意力全部落在「音在五线谱的哪个位置」上；
一旦画上符尾，识别难度会突然跳到「这是八分音符吗」这种时值问题上。

> 曾经的实现给每个音都画了八分音符符尾 —— 那是错的。
> 现在 `StaffNote` 的 `noteValue` 默认 `'whole'`，只有显式传 `half` / `quarter` 才会画符干。

**第 3 档换成二分音符（空心头 + 符干）。这不是时值教学，是形态迁移。**

理由是补掉一个真实落差：只见过全音符的孩子翻开《小汤》会看到带符干的谱子。
符干方向由音高位置决定（三线以上朝下），**不需要额外判断**，
所以它不给「该按哪个键」增加任何信息 —— 认知负担几乎为零，但形态对上了真教材。

**这条区分很重要，别把形态当成难度变量：**

- 档位升降的**唯一**变量是音域。同一个练习里只有一条难度曲线，孩子失败的原因是唯一的
- 所以界面文案里**不出现**「二分音符」字样 —— 一旦写出来，就等于告诉孩子这是要考的东西
- 形态由 `NOTATION_LEVELS[].noteValue` 声明（`staffLayout.ts` 里的 `NoteValue` 类型），
  由 `noteValueForLevel()` 取出。`StaffNote` 只负责按形态绘制，不参与难度决策

时值本身**不在这个练习里教**：跟弹模式已经在做真实的节奏判定（`timingWindowScale`），
那是「听着弹」的时值训练，比「看图算拍子」有效得多。识谱卡片的职责保持纯粹。

### 按水平出题：音域分三档

认谱的难度主要由**音域**决定，所以档位按「加线」来分（`staffLayout.ts` 的 `NOTATION_LEVELS`）：

| 档 | 音域 | 音符形态 | 新增的认知负担 |
| --- | --- | --- | --- |
| 1 | E4 – F5（谱表以内） | 全音符 | 只认 5 线 4 间，没有任何加线 |
| 2 | C4 – F5 | 全音符 | 引入下加一线的中央 C |
| 3 | C4 – G5 | 二分音符 | 谱表上下都出现加线位置 |

- `levelForRound(round, total)` 按题号自动升档（6 题 → 1–2 题第 1 档、3–4 题第 2 档、5–6 题第 3 档），
  难度**只升不降**
- ⚠️ 出题池还要和**当前键盘档位**取交集：8 键键盘只覆盖 C4–C5，
  第 1 档里的 D5 / E5 / F5 它根本弹不到 —— 不取交集就会出一道物理上无法作答的题。
  这一步由 `StaffReadingPage.poolFor()` 完成，`staffLayout.test.ts` 有对应断言
- 引导优先：谱面默认显示各线音名参考（E G B D F），这是「熟悉」而不是「考试」（§43 L2）

### 数字简谱与唱名拼音

需求原文：「如果 1 代表 do、2 代表 mi，把五线谱上对应的简谱数字和拼音也显示出来，这样印象会更深刻。」

> 这里用户口述有一处口误：正确对应是 **1=do(C) 2=re(D) 3=mi(E) 4=fa(F) 5=sol(G) 6=la(A) 7=si(B)**。
> 实现按正确对应执行。

- `noteToSolfege()` → `1 2 3 4 5 6 7`（升号写作 `♯1`）
- `noteToPinyin()` → `do re mi fa sol la si`（用 `sol` 而不是 `so`，与国内教材一致）
- 两个标签画在**音符头的正下方、同一个 x 上**。
  空间对齐就是教学：视线从音符垂直往下，「位置 = 数字 = 读音」一次建立。
  数字外面加一个方框，与简谱的书写习惯一致。
- **设置里可开关**（`AppSettings.showSolfege` / `showPinyin`，默认都开）：
  认熟之后关掉就变成纯识谱练习。老存档没有这两个字段时按「打开」补上（`migrations.ts`）。

### 修过的故障二：数字简谱 / 唱名拼音被「切掉」

**现象**：谱面下方的唱名拼音看着像被遮挡 / 被切。

**根因（用真机尺寸量出来的，不是猜的）**：标签块的纵向位置是按**加线空间**算的固定值，
而 viewBox 底边只按加线算，**没有把文字本身的高度算进去**：

```text
viewBox 底边                        y = 126.00
拼音墨迹下缘（getBBox 实测）        y = 126.84   ← 已经跑出 viewBox
```

于是文字画在了 SVG 视口之外，只靠 `.staff { overflow: visible }` 才看得见。
这条路在 iOS 上不可靠（字体度量不同会把墨迹推得更低；部分 WebKit 版本会照旧裁切视口），
表现就是「拼音被切掉」。同一份几何在 Chrome 里看不出问题，所以一直没被发现。

顺带还有两个由同一个根因带出来的毛病：

- 标签被顶到卡片底边，只剩 15px 就被切
- 谱面底边与标签之间空着 83px（为 A3 预留的加线，而出题音域最低只到中央 C）

**修法**：把标签版式变成**纯几何**（`staffLayout.ts` 的 `createStaffLabelLayout` /
`createStaffViewBox`）：

| 做法 | 为什么 |
| --- | --- |
| 每个标签占一个**固定高度的盒子**，文字在盒内居中 | 纵向布局不再依赖字体度量 |
| 基线 = 盒中心 + `0.35em`，**不用 `dominant-baseline`** | 各浏览器/字体对 `central` / `middle` 的解释不一致，而这个练习要求标签与音符头严格对齐 |
| 字号由 `LABEL_FONT_SIZE` 常量经 SVG 属性给出，**CSS 里不写 `font-size`** | CSS 的 `font-size` 会**盖住** SVG 表现属性（表现属性优先级最低），两边一旦不一致文字就会跑出盒子 |
| viewBox 底边 = 标签块底 + 4 单位 | 标签块**完整包含在 viewBox 内**，不再依赖 `overflow: visible` |
| 内容底边按中央 C（步数 -2）而不是 A3 | 干掉 83px 死空间，谱面顺带变大 |

修完实测：拼音墨迹距 viewBox 底边 **余量 9.9px**（之前是 −1.7px），距卡片底边 27px。

> 有一条测试专门钉住这个不变量：三种标签开关组合下，文字的保守墨迹范围
> （基线上 0.75em / 下 0.25em）都必须落在 viewBox 内。
> 另有一条断言「每一档出题音域的每个音及其加线都在 viewBox 内」，
> 以后往 `NOTATION_LEVELS` 加更低的音会当场失败。

### 修过的故障三：横屏 iPad 的琴键仍然很矮

**上一次只修了一半。** 竖屏从 150px 修到了 431px，但横屏只有 158px ——
因为谱面按**内容高度**要占 291px，一屏 810px 里剩下的才轮到键盘：

```text
横屏 iPad 810px：top 56 + 谱面 291 + 键盘 158 + prompt 96 + hint 30 + gaps 36 ≈ 667
```

**修法**：竖向空间按「谱面 ≤ 1/3、键盘 ≥ 2/3」分，谱面本身横向铺满
（下一节《改版》是最终形态，这里是当时的中间状态）：

```css
.chl__stage > .staff {
  flex: 0 1 auto;
  width: 100%;
  max-height: 34%;
}
```

实测（iPad 810×1080 / 1080×810，Chrome 真实布局引擎）：

| | 琴键高度 | 谱面 |
| --- | --- | --- |
| 竖屏 最初 | 150px | 卡片 329.5px，谱面 340px 宽 |
| 竖屏 现在 | **556px** | 无卡片，谱面 778px 宽（占 96%） |
| 横屏 最初 | 158.5px | 卡片 329.5px |
| 横屏 现在 | **267px** | 无卡片，谱面 1048px 宽（占 97%） |

横向的空白一并解决：谱面本身铺满可用宽度，不再有「卡片拉满、内容很小」的反差。

> 参考：同一台设备上「跟弹」的键盘是 800px、「听音找键」是 725px。
> 看谱找键多了一张谱面，所以是 556px —— 差异来自多出来的那个元素，是合理的。

### 改版：去掉谱面卡片 + 谱面改成横向一行

需求原文：「删除 `div.staff-panel` 卡片填充色块，`svg.staff` 做成左右排版」。

**做了什么**

| 删除 `.staff-panel` 卡片外壳 | 谱面直接铺在舞台底色上。卡片给出一块与内容无关的填充色块，而谱面本来就是「纸上的谱」，自己就能立住（§3.3 不要把每个模块都做成卡片）；顺带少了一个 DOM 层 |

### 修过的故障：看谱找键的琴键在 iPad 上很矮

**现象**：只有「看谱找键」的琴键很矮，「听音找键」正常 —— 同一份键盘组件、同一份 CSS。

**根因**：`.chl__stage` 用 `grid-template-rows: auto minmax(0, 1fr) auto`，
而 grid 的行是**按子元素顺序**分配的；舞台里的谱面与「刚才的音」都是**条件渲染**的。

```text
听音找键：prompt / keyboard / hint
          → 键盘在第 2 行 = 1fr  ✅

看谱找键：prompt / 谱面 / keyboard / hint
          → 键盘被挤到第 3 行 = auto ❌
```

`auto` 行高度**不确定** → `.pk-frame { height: 100% }` 无法解析
→ 琴键退回 `.pk` 的兜底 `min-height: 150px`。同时 `1fr` 行被谱面独占，
谱面在多余空间里被拉得很高、留白很多，进一步放大了反差。

> 注意这是**既有缺陷**，不是五线谱标签改动引入的：行的归属只由子元素个数决定，
> 谱面这一项存在的那一天起就是这样。

**修法**：`.chl__stage` 改成 flex 列，剩余空间由 `flex-grow` 显式指定，与子元素个数无关
（见 `AGENTS.md` §9）。

**为什么当时没测出来**：jsdom 没有布局引擎，`getBoundingClientRect()` 恒为 0，
渲染测试能过、真机上才是坏的。所以补的是**扫 CSS 源码**的不变量守卫
（`src/features/challenges/challengesLayout.test.ts`），而不是渲染测试。

## 长按与文字选择（硬性规则，见 `AGENTS.md` §8）

**整个应用都不允许系统自带的「长按选取文字 / 放大镜 / 呼出菜单」。**

### 触发场景

iPad 上按住琴键稍微久一点，iOS 就进入文字选择模式：弹出放大镜，
并且**吃掉后续的 pointer 事件** —— 表现是「按着按着音就哑了」，
严重时 `pointercancel` 被吞掉，琴键还会停在按下态。

这个应用的主要使用方式就是**按住琴键不放**（「跟弹」的按住提示、自由弹、试听），
所以长按被系统抢走不是外观问题，而是**交互被系统中断**的功能问题。

### 落地方式

`src/styles/base.css`：

```css
html,
body,
#root {
  user-select: none;
  -webkit-user-select: none;
  -webkit-touch-callout: none;
}
```

**为什么必须写在文档根节点**：`user-select` 是**继承**属性。
之前只写在 `.pk` 与 `button` 上，长按只要落在没有该声明的文字节点
（音符卡片、提示文案、页面留白）上，系统一样会进入选择模式。
写在根节点上就覆盖了所有文字节点。

- 逃生口：确实需要复制文字的极少数地方加 `.is-selectable`
  （原本的 `.no-select` 工具类从未被使用，已删除）
- 原本 `.pk` 上的 `touch-action: none` / `-webkit-touch-callout: none` 保留：
  根节点管「选择」，`.pk` 额外管「滚动与缩放」，职责不同
- `PianoKeyboard` 的 `onContextMenu` 屏蔽保留（桌面右键 / iPad 长按菜单）

### 守不住的地方要说清楚

这条**只在真机上才看得出来**，jsdom 永远不会复现。所以做了两件力所能及的事：

1. `browser-compat.test.ts` 的守卫：文档根节点必须有这三条声明，
   并且**任何其它 CSS 都不许再写 `user-select: text / auto / all`**
2. 人工验收清单（见下方《真机验收清单 · 交互》）

## 音色预设（三角钢琴 / 立式钢琴 / 电钢琴）

需求原文：「现在是电子琴的音效，我想有一套模拟钢琴或者电钢琴的音效。」

### 先说「为什么听起来像电子琴」

原来的 `PianoSynth` 已经做了六件对的事（谐波列 + 非谐性、双段衰减、同音多弦拍频、
按住持续衰减、制音器落下的指数衰减、击弦噪声）。**缺的是第七、第八件**：

| 缺什么 | 为什么会听起来像电子琴 |
| --- | --- |
| **力度只改音量，不改音色** | 真钢琴敲得越重，高次分音被激发得越多（频谱倾斜变平）。原来的 `brightnessScale` 给所有 k≥3 的分音乘**同一个倍率** —— 那不是「音色在变」，只是「声音变大变小」 |
| **没有琴体共鸣** | 音板 / 箱体在几个频率上共振，给声音一个木头骨架。完全没有共鸣的干声就是采样器里的干声 |

### 做法：把音色变成**数据**

新增 `src/core/audio/voicePresets.ts`：每套音色声明自己的频谱滚降、力度倾斜曲线、
余音时长、制音器快慢、拍频、琴体共振峰、颤音、击弦噪声。
`PianoSynth.ts` 退化成「照着预设把音造出来」，**自己不含任何音色参数** ——
加一套音色只改 `voicePresets.ts`，不用碰合成器。

顺手补上的两件事：

- **琴体共鸣**：一串 peaking 滤波器（音板 / 箱体的共振峰）
- **力度 → 频谱倾斜**：`(k/3)^指数`，指数随力度从负到正。
  支点取 k=3，因为钢琴前两个分音几乎不随力度变化，变化发生在更高的分音上

### 三套音色的实测指纹

基频归一为 0 dB（`k` 为分音序号）：

| | 2 | 3 | 5 | 10 | 频谱重心（轻→重） | 余音 C4 | 颤音 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 三角钢琴 · 轻触 | −10 | −15 | −24 | −37 | 2.45 | 6.5s | 无 |
| 三角钢琴 · 重击 | −10 | −15 | −21 | −29 | 3.39（**1.38×**） | | |
| 立式钢琴 · 轻触 | −12 | −19 | −29 | −43 | 1.91 | 4.5s | 无 |
| 立式钢琴 · 重击 | −12 | −19 | −27 | −37 | 2.27（1.19×） | | |
| 电钢琴 · 轻触 | −16 | −25 | −39 | −45 | 1.57 | 6.7s | 4.6Hz |
| 电钢琴 · 重击 | −16 | −25 | −31 | **−27** | 2.96（**1.89×**） | | |

三套的性格差别都能从表里读出来：

- **三角钢琴**：亮、共鸣丰富（4 个共振峰）、余音最长
- **立式钢琴**：更暗（16 次分音 −44 dB vs 三角琴 −34 dB）、箱体感更重（共振增益合计 12.1 dB vs 9.6 dB）、
  余音短一些；调音偏差也更大（±3.4 音分，家用琴本来就不那么准）
- **电钢琴**：频谱干净得多（2 次分音 −16 dB），但在 **k=10 有一个「铃」**：
  轻触时 −45 dB（几乎听不到），重击时 −27 dB —— **18 dB 的跳变就是电钢琴的 bark**。
  单根齿所以**没有拍频**，另有 4.6Hz 的颤音（电钢琴的经典特征），没有毛毡击弦噪声

### 默认听感没有变

三角钢琴预设的力度倾斜取 `-0.62 + 0.9v`，在默认力度 0.85 处倍率约 **1.19** ——
与原实现（`0.55 + 0.75v` = 1.19）几乎一致。所以默认音色听感不变，
只是**多出了动态范围**（原来几乎没有）。17 条音色回归测试一行没改就全过，
这就是这一点的证据。

### 切换器

设置页「声音与手感」组里，和「节奏判定」并排（「键盘档位」控件已随档位收敛删除）。落库在
`AppSettings.voicePreset`（**存档契约**：选了音色下次打开还应该是它），
老存档没有这个字段时回落到三角钢琴，不认识的 id 也回落（`migrations.ts`）。

同步点是 `ProgressStore` 的那个 effect（与音量同一处：*音量与音色属于音乐引擎，不属于 React*）。
切换**只影响之后按下的键** —— 正在响的音继续用旧音色自然衰减完，
真实琴上换音色本来也不该把正在响的音掐掉。

> 音色与**皮肤**是两件事：皮肤是外观材质（只覆盖 `--skin-*`，§11.1），
> 音色是声音。两者互不影响，也不做联动。

## 修过的故障：连续按键盘出现嘈杂的破音（数字削波）

需求原文：「连续不断按键盘会有嘈杂的音效出现。」

### 定位方式：离线渲染 + 量峰值，不靠耳朵猜

`scripts/flows/audio-clipping.js` 在页面里 import 应用**自己的** `PianoVoice` / 音色预设 /
`mixHeadroom`，用 `OfflineAudioContext` 搭一条与 `AudioEngine` **完全相同**的信号链，
按真实节奏弹一串音，再统计峰值与触顶样本数。

**修复前（音量 0.8）**：

| 场景 | 峰值 | 削波样本 |
| --- | --- | --- |
| 单音 | 0.952 | 0 |
| 三音和弦 | **1.292** | 109 |
| 八音全按 | **1.196** | 334 |
| 连续单音 16 下 | **1.012** | 10 |
| 八键连按 4 轮 | **1.102** | 213 |

**24 个场景里 21 个在削波**（最大峰值 1.608，音量开到 1.0 时更糟）。

### 根因

`PianoVoice` 的所有分音都是**同相位起音**的（所有振荡器都从相位 0 开始），
所以**单个音**的瞬时峰值就已经接近分音振幅之和 ≈ 0.95 —— **一个音就把满刻度用完了**，
再来一个必然溢出。1.0 以上会被输出端直接截平，产生大量高次谐波，
听感就是「嘈杂 / 破音」。

### 两道防线（`src/core/audio/mixHeadroom.ts`）

1. **总线余量 `PIANO_BUS_HEADROOM = 0.35`** —— 把整块键盘先压下来，给和弦留出空间。
   取值不是拍的：量了 0.55 / 0.45 / 0.35 三档，**余量越大，软削波把和弦压得越狠、
   单音与和弦的响度差就越平**（0.8dB / 1.0dB / 1.9dB），所以取 0.35 —— 削波消失的同时
   动态保留得最多。
2. **末端软削波：音量之后、输出之前** —— 0.7 以下**完全线性**（正常弹奏一点不压缩），
   之上用 tanh 软拐点渐进压回，且值域有严格上界 `1 − 1e-6`。
   放在音量**之后**是关键：不管音量开到多大、同时按下多少个键，输出都不可能触顶。

⚠️ **为什么不用压缩器当限幅器**：它不是砖墙限幅器。实测把原来那台
（threshold −10dB / ratio 6 / attack 3ms）配好之后，八音和弦的输出**仍然到 1.19** ——
起音瞬态在 attack 时间里直接穿过去了。压缩器现在只负责「减少饱和程度」，保底靠波形整形。

### 修复后

| | 修复前 | 修复后 |
| --- | --- | --- |
| 削波场景数 | **21 / 24** | **0 / 24** |
| 最大峰值 | 1.608 | **0.982** |
| 音量为 1.0 时 | 全部削波 | 全部不削波 ✓ |

代价：单音比原来轻约 **4dB**（音量设置可以补回 2dB）—— 换来的是八音和弦、
连续快弹、音量拉满全都不再破音。

### 顺带：三套音色做成「等响」

量的时候发现电钢琴比三角钢琴**低 4.7dB** —— 切过去会以为「坏了」。
于是给预设加了 `outputGain`（三角琴 1.0 / 立式 1.05 / 电钢琴 1.7），
重新量一遍：**0 / 0.1 / −0.2 dB** ✓ 换音色不再顺带换音量。

## 三角钢琴 / 立式钢琴听起来不一样（第二轮：形状，不只是明暗）

需求原文：「目前三种…三角钢琴和立式钢琴音色差别不大，查找是否有开源的免费音效可以使用
或者手动改进音效模拟真实声音。」

### 为什么原来「差别不大」

原来两套预设的差别基本只有**频谱斜率**（滚降 1.6 → 1.95）、余音长短、滤波截止。
那听起来是「同一台琴蒙了块布」，而不是另一台琴 ——
**决定「像哪台琴」的是共振的形状，不是明暗。**

### 做法：把琴体共鸣从「每个音一份」搬到总线上，用省下的预算做形状

琴体共鸣模拟的是**同一块音板**，跟弹哪个音无关。原来每个发声的音都建 5 个双二阶滤波器 ——
同时按 8 个键就是 40 个滤波器。搬到总线共享之后：

- **数学上完全等价**（线性时不变滤波器与求和可交换：`filter(Σ音) ≡ Σfilter(音)`）
- 整台琴只有 5 个滤波器，iPad 上省下一大笔
- 于是每个预设可以放心做**5 段塑形**，而不用只在明暗上做文章

### 两套琴现在是「两种形状」

| 频段 | 三角 | 立式 | 差 |
| --- | --- | --- | --- |
| 140 Hz | −11.0 | −8.8 | **+2.2** |
| 330 Hz | −13.0 | −7.8 | **+5.2** |
| 620 Hz | −20.0 | −14.8 | **+5.2** |
| 1300 Hz | −18.5 | −30.0 | **−11.5** |
| 2600 Hz | −29.3 | −44.5 | **−15.2** |
| 3800 Hz | −37.1 | −51.8 | **−14.7** |

- **三角琴**：低频厚、中低挖一个坑（去盒子味）、高频通透（开盖）
- **立式琴**：低频隆起、**中低一个大包（箱子嗡嗡的 honky）**、上部被挖掉（没盖）

**客观指标**：平均频段差 **5.4 dB**，最大 **18.9 dB**。
判据是「平均 < 3dB 基本听不出是两台琴，> 5dB 会明确是两种乐器」。

除了频率形状，另外几项也按真实乐器拉开了：

| | 三角 | 立式 | 理由 |
| --- | --- | --- | --- |
| 非谐性 | 0.0001 | **0.00042（4.2×）** | 立式琴弦短，分音本来就偏得多 —— 这是最强的「立式琴」线索 |
| C4 余音 | 7.6s | **2.8s** | 弦短、音板小 |
| 拍频 | 1.4 音分 | **3.4 音分** | 立式琴的调音更不干净，嗡嗡的 |
| 动态范围 | 2.5× | **1.5×** | 家用立式琴弹不出三角琴的强弱对比 |
| 低频击弦噪声 | 0.06 | **0.125** | 击弦机就在手边，箱体小，「咚」更重 |

### 量出来的东西在哪

```bash
npm run shot -- "#/" --script scripts/flows/preset-spectrum.js   # 逐频段频谱差
npm run shot -- "#/" --script scripts/flows/preset-loudness.js   # 三套等响
```

- 频谱：用 Goertzel 量 13 个频段在起音段的能量，最大值归一
- 等响：三套现在相差 **0 / 0.1 / 0.5 dB**（`outputGain` 按这个工具的结果填）

> 琴体共鸣一改，整体电平和相对响度都会变 —— **改完必须重跑这两个脚本**，
> 并且重跑 `audio-clipping.js` 确认没有削波。

## 采样音源调研（结论：可行，等产品决策）

需求里问到「是否有开源的免费音效可以使用」。查证结果如下（许可证与体积都是实测/官方页面数据）：

| 来源 | 许可证 | 体积 | 格式 | 备注 |
| --- | --- | --- | --- | --- |
| **FreePats Acoustic Grand Piano** | **CC0 1.0（公有领域，无需署名）** | **2.9 MiB**（2 力度层）／ 32 MiB（完整） | SFZ + FLAC/WAV/SF2 | 最干净的选择：CC0、有现成的「小体积 2 力度层」版本 |
| **Salamander Grand Piano V3**（Alexander Holm） | CC BY 3.0（**必须署名**） | **5.22 MB**（单力度层） | MP3，**每小三度一个采样**（A0–C8，30 个文件） | 已打包成 npm：`@audio-samples/piano-mp3-velocity*` —— 直接 `npm install` 就有，MP3 能被 iOS 直接解码 |
| FreePats Upright Piano KW | 需逐个确认 | 中等 | SFZ | 正好补「立式琴」这一档 |
| VCSL Keys / Karoryfer 部分音色 | 部分 CC0 | 中等 | SFZ/WAV | Karoryfer 有若干 CC0 音色 |
| [CC0-Samples-List](https://github.com/LoveBodhi/CC0-Samples-List) | — | — | — | 已核验的 CC0 音源索引，可用来继续找

### 本机条件（已确认）

- **ffmpeg 9.0 已安装** ✓ 所以 SFZ/FLAC/SF2 → MP3/AAC 的转码与裁剪可以本地完成
- 当前整站产物只有 **337 KB**；上面那些是 **2.9–5.2 MB**，也就是整站的 **9–15 倍**

### 建议的做法（如果要做）

不做「整包塞进去」，而是照 `scripts/extract-bravura-glyphs.mjs` 那条路走：
**写一个生成脚本，从 CC0 音源里抽一个很小的子集**。

按本项目实际用到的音域（8 键 = C4–C5，13 个半音）估算：

| 参数 | 取值 | 体积估算 |
| --- | --- | --- |
| 采样间隔 | 每 3–4 个半音 1 个采样 → 11–15 个文件 | — |
| 力度层 | 2 层 | ×2 |
| 单文件 | 单声道、44.1kHz、96kbps MP3、截到 ~2 秒 | ~25 KB |
| **合计** | | **约 550–750 KB** |

代价与前置条件：

1. **体积**：整站从 337 KB 变成约 1 MB（3×）—— 可以接受，但首页要**懒加载**，
   不能阻塞「打开即弹」
2. **加载**：`fetch` + `decodeAudioData`（首帧前要有合成音色兜底，否则第一下没声音）
3. **变调**：`playbackRate` 移位（±1.5–2 个半音以内音色还站得住）
4. **署名**：CC BY 需要一处 credits；**CC0 完全不需要** —— 所以优先 CC0
5. **工作量**：生成脚本 + 加载器 + 力度层选择 + 离线缓存，约 2–4 天
6. ⚠️ **我无法试听**：采样的音质、循环点、噪声底只能由人来判断。
   代码可以保证「加载、变调、分层、兜底」正确，**无法保证「好不好听」**

### 我的建议

**优先做上面这一轮的合成改进**（已经做了，可量、零体积、可随时微调），
把采样作为**第二步的选项** —— 它的收益上限更高，但要先接受三件事：
约 1 MB 的体积、2–4 天工作量、以及**必须由你试听后才能定稿**。

需要的话我可以先只做「生成脚本 + 一个采样预设」，用 1 个力度层、11 个采样
（约 300 KB）验证「采样确实明显更真」，再决定要不要铺满。

## 音区选择

> ⚠️ **已作废**：本节描述的功能随「只保留 8 键」一起删掉了（见《只保留 8 键》）。
> 下面的实测数据仍然成立，作为当时判断的依据保留。

**原计划是「练习页加一个高/低八度按钮」。量完之后发现那个按钮会是个空动作，于是改成「有第二个音区才出现」。**

### 为什么不能照原计划做

`resolveSong()` 对越界的音会**按八度吸附回来**（`octaveFit`，保持唱名不变，听感最自然）。
于是「把整首歌移高一个八度」在整首歌本来就放得下的时候，会得到**完全相同的声音**：
每个音都被吸附回原位。一个按下去不改变任何声音的按钮，比没有按钮更糟。

所以先加了两个纯函数，把「这个档位到底有没有用」变成可计算的：

- `feasibleOctaveShifts(song, size)` —— 每个音都真实落在琴键上（**完全不需要吸附**）的八度位移
- `transposeChoices(song, size)` —— 练习页可用的相对档位（升序，含默认的 `0`）；
  只返回 `[0]` 就表示**没有第二个音区可去**

### 实测：8 键（初学档）没有第二个音区

| 键盘 | 有第二个音区以上的曲目 | 可行位移 |
| --- | --- | --- |
| 8 键（C4–C5） | **0 / 10** | 只有 `0` |
| 15 键（C3–C5） | 8 / 10 | `0`、`−12` |
| 25 键（C2–F5） | 10 / 10 | `0`、`−12`、`+12`、`−24` |

练习页的规则因此是：**`transposeChoices().length > 1` 才渲染控件**。
8 键（孩子第一次接触钢琴用的档位）看不到它 —— 这不是漏做，而是那里根本没有可选项。
15 / 25 键上它出现为顶栏的「低 / 原 / 高」，**与速度档共用同一套分段控件样式**
（`.pp__tempo, .pp__octave` 同一组规则；同一个位置不该长出第二种外观）。

### 必须连带做的两件事

- 换音区要**重置这一轮**：否则谱面与提示音会在孩子弹到一半时整首换掉
- 换键盘档位要**把音区归零**：档位变了，原来选的音区可能已经不存在

### 守卫

`src/features/songs/songRegisters.test.ts` 守住「按钮永远不是空动作」：
对每个键盘、每首曲目、每个给出的档位，断言 `resolveSong()` 的结果里
**没有任何一个音 `adjusted === true`**；同时用一条测试把「不可行档位会被原路吸附」
这个证据本身钉住 —— 将来如果谁放宽了 `octaveFit`，那条测试会先失败。

## 滑动琴键的嘈杂音（第三次才修对，因为前两次都在量错的东西）

> ⚠️ **读数说明**：15 / 25 键已移除（见《只保留 8 键》）。8 键实测密度是 79ms 一个音，
> **已经高于限速阈值 65ms，所以限速现在不会触发**；滑奏的音仍然按 0.6 力度发声。
> 下面保留 15 / 25 键的读数，作为当时定位问题的依据。

**症状**：手指在琴键上连续滑动时声音嘈杂；8 键还好，15 / 25 键明显更糟。
**之前没修好**，因为前两次都在**电平**上找原因。

### 被排除的四个假设（都是实测）

用 `scripts/flows/glissando.js` 离线渲染同一条链两次（带 / 不带软削波），
25 键快速滑动 ＋ 逐个换掉一个变量：

| 假设 | 实测 | 结论 |
| --- | --- | --- |
| 输出削波 | 削波前峰值 **0.93**、超拐点样本 3.1%、RMS 损失 **0%** | ❌ 软削波几乎没工作 |
| 击弦噪声叠成嘶声 | RMS 0.272 → 0.272 | ❌ |
| 制音器尾巴堆积 | 制音器改 0.12s：RMS 0.270 | ❌ |
| 混响糊成一片 | 关掉混响：RMS 0.274 | ❌ |
| 声部堆积（掐掉上一个音） | RMS 0.272 | ❌ |

顺带发现两件事：**前两次「削波验收」都漏了琴体共振（cabinet）**——
真实链条里它在总线上（`+3.2dB@90Hz`），补上之后超拐点只从 2.6% 升到 3.1%，
所以它也不是主因；而软削波接上之后**「硬削波样本数」这个老指标恒为 0，等于失明**。

### 真正的原因：手势被当成了 N 次独立按键

用 `scripts/flows/slide-events.js` 在**真实应用里**打滑动（包一层 `audioEngine.noteOn/noteOff` 记账）：

| 键盘 | 白键宽 | 快速滑动（24px/16ms）实测 |
| --- | --- | --- |
| 8 键 | 97.3px | 8 个音，**79ms 一个（13 个/秒）** |
| 15 / 25 键 | **31.1px** | 25 个音，**24ms 一个（41 个/秒）** |

键越窄，同样手速下**音符密度越高**（键宽 97px → 31px，密度翻 5 倍）。
41 个音/秒、每个都带 0.17s 制音尾巴和一记明亮起音 —— 这不是滑奏，是一片嘈杂。
事件层本身是干净的：**0 次 30ms 内重触发、0 次 A-B-A 抖动**。

### 修法：把滑动当滑奏，而不是改音色 / 电平

只在输入层改（`src/features/piano/useKeyboardInput.ts`）——**音频链一个参数都没动**：

- 上一个键按住不到 `GLIDE_HOLD_MS`(150ms) 就换了键 → 判定为滑奏；
  逐键弹奏每个键都按住几百毫秒，**完全不受影响**
- 滑奏的音按 `GLIDE_VELOCITY`(0.6) 发声：擦过去本来就比按下去轻
- 限速到 `GLIDE_MIN_GAP_MS`(65ms) 一个音；**被挡下的音不丢**，变成「待补发」，
  手指停在该键上就补上（孩子滑到位停住，仍然正常发声）

修复后实测（同一个探针）：25 键快滑 **41 个/秒 → 15 个/秒**；8 键与慢滑**一点没变**。

> 验收提示：真机上在 8 键上快速来回擦，确认听起来是「滑奏的叮咚声」
> 而不是一片沙沙；再在 8 键上逐键弹，确认力度与手感没有被削弱。

### 为什么这是对的（不只是"少做一点"）

- 幼儿启蒙用不到那么多按键：刚学琴的孩子本来就在一个八度里活动
- **只有 8 键能在 iPad 上达到真实钢琴的白键宽度**（八度跨度 164.5mm）。15 个真实尺寸白键需要
  352.5mm，而最大的 iPad 屏幕物理宽只有 263mm —— 更宽的键盘必然是被压缩过的，
  手指跨度反而**无法迁移到真琴**，与「琴键必须是物理尺寸」这条需求直接冲突
- 顺带作废了上一轮做的「音区（移调）」控件：它只在 15 / 25 键上存在第二个可行音区，
  8 键下永远不出现。控件、纯函数（`transposeChoices` / `feasibleOctaveShifts`）与单测一起删除

### 改了什么

| 位置 | 处理 |
| --- | --- |
| `pianoLayout.ts` | `KEYBOARD_SIZES = [8]`（提供给用户的档位）；布局函数仍支持任意白键数，备查 |
| 设置页 / 自由弹 / 练习页 / 自检页 | 档位切换控件全部删除 |
| `migrations.ts` | 旧存档里的 15 / 25 一律回落到 8（不清空、不报错） |
| `songData.ts` / `types.ts` | 删除 `defaultKeyboard` 字段（已无处可切） |
| 曲目列表 | 删掉「建议 N 键」提示（只有一个档位） |
| `scripts/flows/practice-toolbar.js` | 依赖 15 键，作为历史探针保留 |

### 连带发现：曲库必须按 8 键重审

新增一条硬门槛（`songData.test.ts`）：**每首曲目都要能在 8 键上整首放进去** ——
整体移调允许（整首歌同一个位移，旋律不变形），单音被吸附不行。10 首里有两首不达标：

| 曲目 | 问题 | 处理 |
| --- | --- | --- |
| 两只老虎 | 结尾是原曲的**下行五度**（C–G3–C），8 键够不到 | 那个音记成 G4 —— 8 键玩具钢琴上通行的儿童版处理：歌听得出，但结尾的五度朝上 |
| 生日快乐 | 旋律 G3→G4，跨度**正好一个八度**且锚在 G 上；C4–C5 也只有 12 个半音，而只有整八度移调才不产生黑键 → 两头都会掉出键盘 | **暂不收录**（数据留在 `songData.ts` 里并注明原因与两条回归路径） |

所以曲库现在是 **9 首**，且这条门槛由测试守着。

### 黑键：把一个早先的设定改掉了

原先按设计规范「第一次接触钢琴，不出现黑键」把 8 键做成了纯白键。**产品侧发现这是个错误**：
真实钢琴上认 C 靠的是**黑键的分组**（两个黑键左边那个白键就是 C），
一排 8 个一模一样的白键反而让孩子**找不到中央C**。

所以现在 8 键 = 8 白键 + 5 黑键（C#4 D#4 F#4 G#4 A#4），黑键**可以正常按响**：

| 变化 | 说明 |
| --- | --- |
| `pianoLayout.ts` | 去掉 `size !== 8` 这个开关，黑键一律生成；`hasBlackKeys` 按实际数量给 |
| 物理尺寸 | **不变** —— 黑键叠在白键层上，白键宽度还是 97.3px（竖屏 iPad 实测） |
| 曲库门槛 | **不变** —— 曲目仍然全部只用白键（`songData.test.ts` 守着），所以那 9 首不受影响 |
| 按错黑键 | 练习页上就是弹了一个错音 —— 与真实钢琴一致，不再被吞掉 |

黑键不标音名（键窄，标了看不清）；音名与唱名由键盘上方的标注负责。

## 中国风曲目收录约定

**用户需求**：把《中国风钢琴入门教程1》里的曲目加进曲库。

### 为什么不能直接加

教材是**已出版作品**：民歌*旋律*多为公有领域，但**编配（和声、伴奏型、指法、乐句处理）独立受保护**。
这个应用要部署到 Cloudflare Pages 公开访问，把教材编配打包进仓库 / 构建产物就是公开传播他人作品
（完整评估见上文《外挂曲目与 PDF 导入评估》）。

**还有一条同样硬的门槛**：本项目只提供 8 键（C4–C5 全白键），而**转写错一个音就是在教错音** ——
家长不会知道错在哪 3 个音。民歌旋律「哼得出来」不等于能逐音写对，
而能搜到的简谱都是**图片**，无法机械核对。

所以本项目的约定是：**不接受凭记忆写的旋律，哪怕听起来对**。

### 合法且准确的三条路

| 路径 | 做法 | 准确性 | 谁录入 |
| --- | --- | --- | --- |
| **A. 简谱原文 → 机械转换**（推荐） | 把曲谱上的数字谱存成 `content/jianpu/<id>.txt`，用 `jianpu.ts` 转换 + 校验 | 100% | 你贴谱，我转换 |
| B. 先写单八度简易编配 | 按流传版本编配，用练习页「听一遍」逐音校对 | 需人工校对 | 我写，你校对 |
| C. 内容包 + 录入器 | 应用不含教材内容，只提供「照着谱点键录入」的能力 | 100% | 你自己录 |

路径 C 的完整方案与工时（A+B+C+F+G ≈ 5–6 天）见上文评估；内容包存在设备上，不进仓库。

### 本轮已就位的基础设施

- **`src/features/songs/jianpu.ts`**：`parseJianpu()` / `songToJianpu()` / `checkPlayable()` 三个纯函数
- 文本格式：`1=C 4/4` 开头；`1`–`7` 唱名、`0` 休止、`#4`/`b7` 黑键、`1'`/`5,` 高/低八度、
  `-` 延长一拍、`_` 减半、`~` 附点、`|` 小节线
- **`jianpu.test.ts`** 守住三件事：曲库每首都能「数据 ↔ 简谱」往返不丢信息；
  每首都完全落在 8 键上（不需要吸附）；**小节线是真小节线**，能查出错拍的小节 ——
  这正是人工录入最容易出错的地方

### AI 读谱：评估过，**暂不做**（2026-05 判定）

照片 → 简谱这条路**做过可行性验证**：本机 `qwen3-vl:8b` 能读（自测图 3 行基本全对，约 27s/张），
再加 `parseJianpu()` 的机械校验（小节是否按拍号凑满、音是否落在 8 键上）能自动抓出错拍与越界。

**但结论是不做**：读谱准确率取决于照片质量（反光、透视、印刷），而这是**给孩子的曲谱** ——
错一个音就是在教错音，家长也不会知道错在哪。把这种不确定性放进内容生产链不划算。

**保留的是校验那一半**（`src/features/songs/jianpu.ts` + `jianpu.test.ts`）：
曲目数据 ↔ 简谱文本往返、8 键范围、小节拍数 —— 任何来源的旋律（人工按谱录入、
将来导入 MusicXML / MIDI）都先过它一遍。**这部分不依赖任何模型，纯算术。**

要复活读谱，前提**不是换更聪明的模型，而是拿到带音乐语义的输入**（MusicXML / MIDI）——
见上文《外挂曲目与 PDF 导入评估》。

## 节拍挑战（开发规划 §12.4 · V1）

```text
时间轴 → 目标区 → 用户按键 → 判断命中
```

规格只要求五样东西：**速度 · marker · hit window · combo · result**，
并且明确「不要一开始做成复杂劲舞团系统」。V1 就照这个做。

### 判定是纯逻辑（`src/features/challenges/beatClock.ts`）

时间是唯一会含糊的地方，所以判定全部放进纯函数并用 60 BPM（一拍正好 1000ms）把边界写死：

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 完美窗 | ±90ms | 与跟弹模式的"正好"同量级 |
| 不错窗 | ±180ms | 比跟弹模式宽 —— 孩子第一次学「跟着拍子按」 |
| 每档得分 | 完美 1 / 不错 0.6 / 没跟上 0 | 准确率 = 得分 ÷ 16 拍 |
| 预备拍 | 4 拍 | **只响不判**，孩子先听到速度 |
| 正式拍 | 16 拍（4 小节） | 一轮够短，注意力撑得住 |
| 速度档 | 60 / 80 / 100 拍/分 | 慢档 = 一秒一拍，孩子最容易跟上 |

另外三条刻意的取舍：

- **多按不扣分、也不打断连击**，只在结算里显示「多按了几下」。孩子乱按不该被惩罚
- **预备拍上按下去只算多按**，绝不判分
- **按任意琴键都算一拍**（顺便发出钢琴声当反馈）：音高是「听音找键」的事，不是节拍的事

### 咔声：独立的 `DrumEngine`

开发规划明确要求「不要把鼓音逻辑塞进 PianoEngine」，所以咔声走自己的模块与自己的总线：

```text
DrumEngine(两个正弦 + 2ms 起音 + 55ms 指数衰减) → drumBus(0.32) → limiter → master → 软削波
```

- **不进钢琴的琴体共振**（咔声不是乐器音色，换音色不该改变节拍器）
- 仍然在限幅器之前汇入 → 音量跟着用户音量走，且不可能顶破总输出（§13 的两道防线照样生效）
- 小节第一拍**更高更响**（重拍），孩子才听得出「四拍一组」
- 退出挑战时 `stopMetronome()` 掐掉已排进时间轴的咔声，不留鬼声

### 与全项目一致的时序约定

整轮咔声**一次性排到 `AudioContext.currentTime` 时间轴上**（20 个咔声 = 40 个振荡器，一次排完），
界面只跑 `requestAnimationFrame` —— **没有逐拍 `setTimeout`**。判定用 `performance.now()`：
两个时钟都按真实时间走，只存在一个常数偏移，对 ±180ms 的窗口可以忽略。

### 布局

复用两个小挑战页共用的 `.chl__*` 骨架（`chl__top / chl__stage / chl__prompt / chl__keyboard / chl__bottom`），
新增的只有轨道与速度档：`.chl__track / .chl__hitline / .chl__marker / .chl__speed`。
轨道高度固定 76px 且**放在 `.chl__prompt` 里**，所以「键盘拿走剩余空间」这条不变量不受影响 ——
实测（iPad 竖屏 810×1080，点击开始后的 playing 状态）：键盘仍是 **778×773**，无重叠。

### 守卫

- `src/features/challenges/beatClock.test.ts`：12 条，把判定边界、连击、过期、结算口径全钉住
- `src/core/audio/DrumEngine.test.ts`：5 条，用记账用的假上下文验接线、包络、重拍与「掐声」
  （包络里出现 0 会让真实的 `exponentialRampToValueAtTime` 抛错，这条也测了）
- `routes.smoke`：新增 `#/challenges/beat` 能渲染

### 还没做的（诚实清单）

- 真机手感：咔声与琴键反馈的**主观**听感要你上手试（我把音量放在总线增益 0.32）
- 节拍挑战**不给成长值**（与另外两个挑战一致：挑战不写成长数据，皮肤只由练习事件解锁）
- 变奏谱面 / 多轨 / 连击特效：规格明确不要一开始就做

## 跟弹模式下黑白键「交叉」

**症状**：跟弹模式里被引导的（白）琴键看起来和黑键交叉了。

### 复现与根因（`scripts/flows/key-stacking.js`）

进入跟弹、点「开始跟弹」后测：

```text
引导键=E4(白) z=3 | .pk__whites={position:static, zIndex:auto} .pk__blacks={position:absolute, zIndex:auto}
引导键与黑键几何相交=D#4 | 黑键被盖住=1 → D#4被E4盖住
```

根因不是某个数值写错，而是**两层的层叠上下文缺失**：

- 黑键靠 `.pk-key--black { z-index: 2 }` 压在白键之上（真实钢琴上黑键确实更靠近眼睛）
- 而引导样式 `.pk-key.is-guide { z-index: 3 }` 对**任意**键生效 —— 引导落在白键时，
  那个白键就跨层翻到黑键上面，把黑键切掉一半（视觉），并且**抢走它的命中**（功能）

这个缺陷一直存在，只是以前 8 键没有黑键、15/25 键又不在界面里，所以没被看到 ——
**加黑键把它暴露出来了**。

### 修法：让「层」决定顺序，而不是让「键」决定

| 改动 | 作用 |
| --- | --- |
| `.pk__whites { position: relative; z-index: 1 }` | 建层。白键内部的任何提升都**翻不出这一层** |
| `.pk__blacks { z-index: 2 }` | 黑键层永远在白键层之上 |
| 白键提示点 `bottom` 从 `calc(100% - 26%)`（= 顶部 26%，落在黑键带里）改成 **26%**（黑键带下方） | 否则层序修好之后，提示点会被黑键挡掉一半；而且这里本来就是孩子手指按的位置 |

修复后同一条探针：**黑键被盖住 = 0**，提示点与黑键无相交。

### 守卫

`src/features/piano/keyStacking.test.ts`（读 `piano.css` 断言，jsdom 没有层叠所以只能这样守）：

1. 两层都必须声明 z-index，且黑键层 > 白键层
2. 白键自己不许设置 z-index（抬升只由引导态触发，且只在本层内）
3. 白键提示点必须整体落在黑键带下方 —— 黑键带高度是从 CSS 里**读出来**的，
   改了 62% 这个数，测试会跟着一起判断

## 键盘换成 15 键（中央C 居中）

**需求**：看谱找键里中央C 在最左边 —— 钢琴课第一步教的是「先找中央C」，它不能在边上。

### 先排除的不是这一件事

先量了再说：键盘本来就是**满宽且居中**的（竖屏 x=16 / 左空 16 / 右空 16；横屏 52 / 52），
所以问题不在页面居中，而在**音域**：8 键 = C4–C5 一个八度，中央C 只能是最左键。

### 决定与代价

产品侧选择「中央C 居中」优先于「键宽真实」，所以改成 **15 键 = C3–C5**：
中央C 正好是第 8 个白键（15 个里的正中间），与真琴一致。

| 方向 | 白键宽 | 折合毫米 | 占真实 23.5mm | 黑键 |
| --- | --- | --- | --- | --- |
| 竖屏 810×1080 | 52px | 约 10.0mm | 43% | 10 |
| 横屏 1080×810 | 70px | 约 13.4mm | 57% | 10 |

代价说清楚：**手指跨度不再等于真琴**（这与早先「琴键必须是物理尺寸」那条需求直接冲突），
但界面上 `keySize.ts` 会如实显示「约 10.0mm」并带「约」字 —— 不假装。

### 改动

| 位置 | 处理 |
| --- | --- |
| `pianoLayout.ts` | `KEYBOARD_SIZES = [15]`；8 / 25 键的布局代码保留备查 |
| `progressTypes.ts` / `migrations.ts` | 默认档位 → 15；旧存档里的 8 / 25 **一律回落到 15** |
| 曲库门槛 | 断言改为**遍历当前提供的档位**（不再写死 8 键）—— 9 首曲子仍全部原样可弹 |
| 冒烟测试 | `data-keyboard-size` → 15，并断言**第 8 个白键是 C4**（中央C 居中有守卫） |
| 黑键 | 10 个（原本 8 键只有 5 个）；层叠规则不变，`keyStacking.test.ts` 继续守 |

### 顺带修掉的：引导提示点的按高度不变量

15 键让提示点的位置问题暴露出来：提示点高度是**固定 26px**，键盘越矮它占的比例越大 ——
按最矮的键盘（`.pk` 的 min-height = 150px）算，原来的 26% 位置会让它顶进黑键带。
所以位置改到 `bottom: 18%`，并把守卫改成**按最矮键盘算**：

```text
bottom% + (提示点高度 ÷ 最矮键盘高度) + 黑键带% ≤ 100%
```

实测（跟弹模式）：竖屏提示点 y=860 / 黑键下沿 787，横屏 y=625 / 593 —— 都在黑键带下方，无相交。

> 排查这条时又踩了一次**开发服务器缓存**（这次是 CSS）：源码改了但实测位置没变，
> 靠探针打印 `getComputedStyle(dot).bottom` 才分清「CSS 没生效」与「我算错了」，`--force` 重启后正常。
> 已写进 AGENTS §5。

### 还没做的（下一步的自然候选）

键盘现在会**撑满剩余高度**（自由弹页 920px 高 × 52px 宽 ≈ 18:1），
而真实白键的长宽比是 150:23.5 ≈ 6.4:1。也就是说 15 键下琴键变成「细长条」。
按真实比例反推应该把高度压到 `键宽 × 6.4`（52px → 约 333px）——
要不要这么做是视觉决策，等产品侧看过真机再定。

## 真尺寸 + 可拖动的键盘（把中央C 放到中间）

**需求**（产品侧给的方案）：键盘不该被压窄，而「中央C 要在中间」可以用**选取区域**解决 ——
把键盘做成可以横向拖动的，默认把中央C 挪到页面中间。

### 这解开了先前那个死结

小屏上 **键宽真实（23.5mm）** 与 **中央C 在中间** 不可能同时满足：

```text
8 键真实尺寸  → 一个八度，中央C 只能在最左
15 键想居中   → 必须把键压到 10mm（真实尺寸的 43%）
```

允许键盘**宽出屏幕**之后两者兼得：键保持 23.5mm，**视窗位置**决定中央C 出现在哪儿。

### 实现

| 位置 | 改动 |
| --- | --- |
| `keySize.ts` | `resolveWhiteKeyWidth({ allowOverflow: true })`：永不压缩，新增 `overflows` 标记；新增真实长宽比常量 `REAL_KEY_ASPECT = 150 / 23.5 ≈ 6.38` |
| `PianoKeyboard.tsx` | 用 allowOverflow 算宽度；高度按 `键宽 × 6.38` 反推并用可用高度封顶；**默认把 C4 滚到视窗中间**；引导键被拖出视窗时把它带回来 |
| `piano.css` | `.pk-frame` 变成横向滚动容器（`overflow-x: auto` + `touch-action: pan-x`），且溢出时**不能用 justify-content: center**（会把左边裁掉且滚不到，flex + overflow 的已知行为），居中由 `scrollLeft` 决定 |
| 各页容器 CSS | 装了键盘的容器全部补上 `min-width: 0`（见下） |

### 踩到的坑：页面被键盘撑宽

第一次量出来是「键盘 1832px、**页面**横向溢出 1038px、中央C 偏移 527px」——
滚动跑到页面上去了，视窗居中自然失效。

祖先链读数给出了原因：`main.free__stage(cw1832 min-width:auto)` ——
**flex / grid 子项的 `min-width` 默认是 `auto`，不肯缩到比内容更窄**，
于是被宽出屏幕的键盘撑开。给所有装键盘的容器补 `min-width: 0` 之后才正确。

### 实测（iPad）

| 方向 | 白键宽 | 中央C 偏移 | 可拖动 | 键盘高 | 页面溢出 |
| --- | --- | --- | --- | --- | --- |
| 竖屏 810×1080 | 122px = **23.5mm** | **0px** | 1054px | 780px（真实长宽比） | 0 |
| 横屏 1080×810 | 122px = **23.5mm** | **0px** | 784px | 650px（可用高度封顶） | 0 |
| 跟弹 竖屏 | 122px | **0px** | 1054px | 512px | 0 |

怎么拖动：**按琴键仍然是弹音**（`.pk` 的 `touch-action: none` 保证不被滚动抢走），
拖键盘**上下留白**即可左右平移；键盘高度按比例算，所以留白是必然存在的。

### 顺带：真机自检加了「键盘结构」一行

`#/tuning` 新增一行**直接数 DOM** 的读数：`15 键 · 白 15 · 黑 10`。
这是为了排查只在真机上出现的现象：**白 15 / 黑 0 = 拿到的是旧页面**（刷新即可），
**白 15 / 黑 10 = 黑键渲染了但看不见**（那才是渲染 / 层叠问题）。猜不出来时，先看这一行。

## 琴键材质：缝隙与前脸要有实体感

**反馈原文**：按键的阴影做的真实一些，目前的阴影和间距看起来太细太窄。

原来是一根 1px 的分隔线 + 4px 的底边，平铺 15 个键看起来像「一张纸上画的格子」。
真琴不是这样：白键之间有约 1mm（≈3px）的缝，前端还有一个**比顶面暗的「前脸」**
（键的前端是另一个面），黑键比白键高出一层、接触阴影更实。

| | 改前 | 改后 |
| --- | --- | --- |
| 白键缝隙（border-right） | 1px | **3px**（`--skin-key-border`） |
| 白键前脸（border-bottom） | 4px | **9px**（`--skin-key-shadow`） |
| 白键圆角 / 接触阴影 | 6px / 无 | 7px / `0 2px 2px`（单层中性） |
| 黑键阴影 / 圆角 / 宽度比 | `0 2px 3px` / 5px / **0.62** | `0 4px 3px` / 6px / **0.58**（= 真实比例，与 `keySize.ts` 的 `REAL_BLACK_KEY_RATIO` 对齐） |
| 按下态 | 下沉 2px、前脸 2px | 下沉 3px、前脸 6px（同一个动作：键被压下去，前脸变薄） |

### 两条必须守住的事（都有守卫）

1. **音距不能变**：`box-sizing` 是 border-box，边框算在 122px 里 ——
   加粗缝隙后白键仍是 **122px = 真实 23.5mm**（实测），变的只是可见键面（121→119px）。
2. **阴影只用皮肤变量**：`var(--skin-key-shadow)`，**单层**、中性色，不硬编码颜色、不彩色发光
   （§7.3 / §33）。换皮肤时阴影跟着走，深色皮肤不会出现「白影」。

`keyStacking.test.ts` 现在守 6 条：层叠 3 条 + 材质 3 条
（缝隙 ≥2px、前脸 ≥6px、阴影来自皮肤变量且不叠层、黑键阴影偏移大于白键）。

## 琴键的立体感与按下手感（去掉琴壳）

**反馈原文**：琴壳删除，把按键的立体感做出来，按下去的效果模拟真实键盘。

琴壳（键盘外面那层座面）去掉了 —— 立体感应该做在**琴键本身**，而不是给它加一个框。
真实钢琴上「一块键有厚度」靠的是两件事，这两件都能在屏幕上做出来：

| 真实琴键 | 屏幕上怎么表达 | 实现 |
| --- | --- | --- |
| **顶面受光、前脸背光** | 键体（`--skin-key-bg`，本身就带一点渐变）+ 前脸（`--skin-key-shadow` 的 `border-bottom`） | 前脸 **9px → 12px**（实测 4px 时整块键像贴纸） |
| **黑键高出一层** | 深色键画不出受光/背光两面，所以立体感来自**它落在白键上的阴影** | `0 4px 3px` → **`0 6px 4px`** |

### 按下：行程 + 时间都要像真键盘

```text
白键：translateY(3px) + 前脸 6px   →   translateY(5px) + 前脸 4px，接触阴影收掉
黑键：translateY(3px) + 阴影 2px   →   translateY(4px) + 阴影 2px
时间：按下 45ms / 回弹 90ms（原来按下也是 90ms，太黏）
```

行程取 5px 而不是按比例缩小：屏幕上一个键 780px 长，真实行程约 10mm（≈52px）放不下，
所以取「看得出来的最大行程」。**按下比回弹快**这条直接用 CSS 的非对称 transition 表达：
基础规则的 `--motion-press`(90ms) 管回弹，`.is-pressed` 里的 `transition-duration: 45ms` 管按下。

**反馈原文**：设置页改成与装扮页一样的排版设置，而不是一个个卡片。

## three.js 3D 键盘：**实验过，已放弃**

**结论（产品侧）**：太丑了，算了。代码已全部撤掉 —— 页面、样式、路由、冒烟断言、探针，
以及 `three` / `@types/three` 依赖本身（不留半个 chunk 在构建里）。

### 实验做到了什么程度（留个记录，免得重复投入）

它确实跑起来了：`#/lab` 里是一块 15 键 3D 键盘，场景单位 = 毫米（白键 23.5 × 150 × 18，
黑键 0.58 倍宽 / 62% 长，键位取自 `getKeyboardLayout(15)`，与 2D 键盘同一份数据）；
立体感是**光照算出来的**（顶面受光、前脸偏暗、黑键在白键上投真阴影）；
按下时键下沉 6mm 并绕后端微转 0.035 rad；声音照旧走 `audioEngine`。
实测 headless Chrome 里 `canvas=778x919 webgl=有`，没有 WebGL 时优雅降级。

### 为什么放弃

- **观感**：产品侧判定不如现有的 DOM 键盘。3D 的真问题不在几何，而在**它把「一块琴键」
  变成了一个透视投影** —— 在 810px 宽的屏幕上，透视会让远处与近处的键不齐，看起来反而更假
- **代价**：换 canvas 要重建三件长在 DOM 上的东西（`elementFromPoint` 命中、每键
  `aria-label`、`keySize`/`keyStacking` 的真实尺寸与层叠守卫），外加一个 500KB+ 的懒加载 chunk
- 收益（更立体）已经由**键材质**那条路拿到了：键缝 3px + 前脸 12px + 黑键投影 + 按下行程，
  成本是一个 CSS 文件

**所以不要重做**：立体感继续走「琴键材质」那条路（见《琴键的立体感与按下手感》），
它是 CSS，能被现有守卫覆盖，也不增加包体。

## 样式表被批量脚本静默截断（事故 + 守卫）

**现象**：`npm run build` 输出里多了一行 `▲ [WARNING] Unexpected "}" [css-syntax-error]`，
指到打包后的 CSS；除此之外**什么都没坏** —— 页面正常、`typecheck` 0 error、全部用例通过。

**根因**：先前批量给键盘容器加 `min-width: 0` 的那个脚本，把
`src/features/tuning/tuning.css` 结尾这段削成了半个：

```css
@media (min-width: 1000px) {
  .tune__body { grid-template-columns: minmax(320px, 1fr) minmax(0, 1.2fr); align-items: start; }

  .tune__keys,
  .tune__sizes {          /* ← 连同这条声明一起被吃掉 */
    grid-column: 1 / -1;
  }
}
```

剩下的 `.tune__keys,` 后面直接跟 `}`（空的规则体，非法）。
`.tune__sizes` 那半是**应当删的**（键盘档位选择器随「只留 15 键」一起下线了），
`.tune__keys { grid-column: 1 / -1 }` 则**必须留着** —— 宽屏下自检页的键盘要横跨两列。

**为什么之前没人发现**：

- **括号是配平的**：`{` 与 `}` 的数量对得上（少了一个 `{`、也少了一个 `}`），
  所以任何「数括号」的检查都抓不到；`vite build` 也不把它当错误
- 视觉影响只在 ≥1000px 的自检页出现（键盘掉进左列），而自检页是家长用的隐藏页
- 唯一的信号就是构建输出里那一行 WARNING —— 而当时只看 `✓ built in`

**怎么定位的**（三步，可复用）：

1. `scripts/css-syntax-locate.mjs` —— 把每个 CSS 单独交给 esbuild，复现警告并打印
   文件名 + 行号 + 上下文（一眼看出是 `tuning.css`）
2. 快照 zip 里是同一份残骸（快照打晚了），所以从**会话记录**里重放：
   `decode-zstd-frames.mjs` + `replay-file-history.mjs` → 拿到脚本改动前的版本，
   读到被吃掉的那条声明
3. 按「哪半该留、哪半该删」修回去：`.tune__sizes` 已无引用（`grep` 全仓库确认），
   `.tune__keys` 的 `grid-column` 保留

### 守卫：`src/test/css-syntax.test.ts`

每个 CSS 文件都过一次 esbuild，**有警告即失败**，并附带括号配平读数。
造一次真实损坏验证过它确实会红：注入同样的残片后报
`features\tuning\tuning.css:244 Unexpected "}"` + `花括号不配平（结尾 depth=-1）`。

两条实现上的注意：

- 该测试**必须 `@vitest-environment node`** —— jsdom 的 `TextEncoder` 属于另一个 realm，
  esbuild 会报 `Invariant violation: ... instanceof Uint8Array`（这不是代码问题，是环境问题）
- 它只抓**语法**。脚本把一整条规则删得干干净净（括号仍配平）时抓不到 ——
  那种情况只能靠 `AGENTS.md` §11 的规矩：批量改样式用 `edit` / Node 脚本，
  不要用带正则的 shell 管道

**收尾纪律**：改完 CSS 之后，构建输出要**逐行看完**，不能只看最后那行 `✓ built in`。

## 排版层级统一（字号 / 行高 / 顶栏 / 版心）

**用户要求**：根据层级关系，统一页面的文字大小与排版。

**先盘现状**（`node scripts/type-audit.mjs` + `scripts/type-map.mjs`，把每个 CSS 的
「选择器 → 字号/字重/行高」全打出来），偏差比预想的多：

| 症状 | 实测 |
| --- | --- |
| 页面标题一层混用两档 | 设置 / 曲目 / 装扮用 `--font-size-h1`；首页品牌名、练习页歌名、挑战页标题、自检页标题却是 `--font-size-h2` |
| 区块标题一层三种大小 | 设置页分组标题 14px、自检页面板标题 16px、导入页与装扮页小标题 18–20px |
| **有失效引用** | `challenges.css` 的 `.chl__combo-value` 写的是 `var(--font-size-title)` —— 这个 token **从未定义**，整条声明静默作废，连击数字一直靠继承 |
| 有「没有字号」的 | `.chl__result-value`、`.song-card__best`、`.tune__trace-note`、`.tune__bars-count` 都没有 `font-size` |
| 自造数值 | 谱面 11px（低于 12px 下限）、完成页 30px、琴键标签 `clamp(12px,1.2vw,14px)`、星星 `clamp(40px,6vw,56px)` |
| 字重 / 行高没走 token | 数字字重 600 ×42、500 ×4；行高原值 7 种（1 / 1.2 / 1.35 / 1.45 / 1.5 / 1.6 / 1.7） |
| 顶栏三种高度 | 首页 64px、工具页 **80px**、练习/挑战页 64px（工具页被 56px 的返回按钮撑高） |
| 版心不统一 | 设置 / 导入 720px，曲目 / 装扮铺满 810px；正文列分区间距 8 / 12 / 16 / 24 四种 |

### 定下来的层级表（真源在 `AGENTS.md` §18，数值在 `tokens.css` 注释里）

```text
一级 · 页面核心标题   display   42–56   完成页标题、星星行
一级 · 页面标题       h1        24–28   所有页面顶栏标题（含首页品牌名、练习页歌名）
二级 · 主要状态数字   metric    32–40   挑战连击 / 判定 / 装扮页成长数值
二级 · 区块标题·主操作 h2        18–20   页内分节标题、大按钮
三级 · 正文           body      16      说明、列表内容、普通按钮
三级 · 辅助文字       label     14      副标题、元信息、统计、次要按钮
四级 · 最小说明       micro     12      脚注、单位、提示（下限）
```

**判据是「这一层在页面任务里排第几」，不是「它长得像标题还是像按钮」。**
所以自检页的面板标题（原本 16px）与设置页的分组标题（原本 14px）都归到区块标题，
统一成 18–20px；设置页的统计数字（原本 20px）是三级辅助信息，降到 14px。
行高同时收敛成 4 档：`none`(1) / `tight`(1.25，标题) / `body`(1.5) / `relaxed`(1.65，多行说明)。

### 改了什么

- **字号**：全部走 token（`font-size` 里不再有任何 px / clamp 原值）
- **字重**：46 处数字 → `var(--font-weight-semibold|medium|regular)`
- **行高**：11 处原值 → 4 档 token；标题另外补 `--line-height-tight`（原本 1.5，标题四周散开）
- **顶栏统一 64px**：两条机制缺一不可 —— 栏内控件 `--tap-target-compact`(44px)，
  栏自身内边距 `var(--space-2) var(--space-4)`。少了第一条顶栏 80px，少了第二条 68px（都实测过）
- **版心**：阅读型页面（设置 / 导入）`--content-max-width` 720px 居中；
  网格型页面（曲目 / 装扮 / 自检 / 挑战）用满可用宽度，靠 `auto-fill` 自适应 —— 这是**两类页面**，不是不一致
- **正文列分区间距**统一 `var(--space-4)`
- **删死 CSS**：首页的 `home__card-*` / `home__recent-*`（首页改成自由弹之后留下的整块）、
  25 键的 `.pk--25`、`.pk--decorated`、未被引用的 `.ui-card` / `.visually-hidden`
  （用 `scripts/dead-css.mjs` 扫出来，`is-down/is-up/is-cancel` 是模板串拼的，不能删）

### 踩到的坑（值得记住）

删「完成页 30px 覆盖」那条规则时，脚本按选择器匹配，把 `.pp-result__title` 的**正规规则**

**是新写的守卫测试当场抓到的**，报错是

### 守卫：`src/test/typography.test.ts`（6 条）

1. `var(--font-size-* / line-height-* / font-weight-*)` 引用必须在 `tokens.css` 有定义（抓失效引用）
2. `tokens.css` 之外不得出现自造字号
3. 不得出现数字字重与原值行高
4. **角色表**：页面标题 / 核心标题 / 状态数字 / 区块标题，逐个断言用的是哪一档 token
5. 顶栏 64px + 栏内控件 44px + 栏内边距，以及正文列分区间距
6. 标题必须用紧行高

**新增页面时先在角色表里登记**：登记不出来，就说明这个元素还没有明确层级。
